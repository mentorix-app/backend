# Персональная видимость блоков программы

**Дата:** 2026-08-19
**Статус:** дизайн согласован, реализация не начата

## Задача

Тренер хочет, чтобы часть блоков в дне программы видели не все назначенные
клиенты, а только выбранные. Остальные блоки остаются общими.

Правила продукта, заданные заказчиком:

1. В блок никто не добавлен → блок виден всем, кому назначена программа.
2. В блок добавлены конкретные клиенты → блок виден только им.
3. В дне обязан оставаться минимум один общий блок.
4. Выбирать можно только среди клиентов, которым эта программа назначена.
5. Снятие программы с клиента убирает его из всех блоков этой программы.

## Контекст

Программа существует в двух зеркальных деревьях:

```text
шаблон:  programs → program_weeks → program_week_days
                  → program_week_day_blocks → program_week_day_block_exercises
версия:  program_versions → program_version_weeks → program_version_week_days
                  → program_version_week_day_blocks → …_block_exercises
```

`publish` копирует шаблон в замороженную версию. `program_assignments` — одна
строка на `(trainer_id, client_user_id)`, ссылается на `program_id` +
`program_version_id`. **Одна версия шарится между всеми назначенными клиентами.**

У дней уже есть `day_key` — стабильный uuid, переживающий publish и discard; по
нему считаются `client_workout_completions`. У блоков такого ключа нет: при
каждом publish id блоков новые.

## Решение

Правила видимости **не входят в контент программы**. Они лежат отдельной
таблицей, привязанной к `program_id` и к новому стабильному `block_key`, и
накладываются фильтром на любую версию при чтении клиентом.

Следствия, ради которых выбран этот вариант:

- изменение списка клиентов не создаёт версию и не требует `sync`;
- клиент, отставший на старой версии, получает актуальное правило;
- назначение программы новому клиенту не трогает контент;
- замороженные версии остаются client-agnostic, без ссылок на `users`.

Отвергнутый вариант — хранить список клиентов внутри блока шаблона и копировать
в версию. Тогда каждая правка списка = `publish-update` + `sync` всем
назначенным, отставшие клиенты видят устаревшие правила, а id клиентов навсегда
остаются в замороженных версиях.

## Данные — миграция `000026_program_block_visibility`

### Стабильный ключ блока

```sql
ALTER TABLE mentorix.program_week_day_blocks
  ADD COLUMN block_key uuid NOT NULL DEFAULT gen_random_uuid();

ALTER TABLE mentorix.program_version_week_day_blocks
  ADD COLUMN block_key uuid NOT NULL DEFAULT gen_random_uuid();
-- затем backfill: сопоставить замороженный блок с блоком шаблона по
-- (week_number, day_number, sort_order) — как 000020 делал для day_key.
-- Несопоставленные строки остаются со случайным ключом от дефолта.
```

`DEFAULT gen_random_uuid()` на обеих колонках — обязательное условие, а не
удобство: существующие `InsertDayBlock` и `InsertProgramVersionDayBlock` про
`block_key` не знают, и без дефолта миграция сломала бы любую вставку блока.

Отдельной колонки `program_id` на блоке нет. Она понадобилась бы только ради
`UNIQUE (program_id, block_key)`, но ни один запрос фичи её не читает, а
уникальность ключа даёт генерация uuid. `program_id` блока достаётся джойном
через `program_week_days`, где он уже лежит.

### Правила видимости

```sql
CREATE TABLE mentorix.program_block_clients (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  program_id     uuid NOT NULL REFERENCES mentorix.programs(id) ON DELETE CASCADE,
  block_key      uuid NOT NULL,
  client_user_id uuid NOT NULL REFERENCES mentorix.users(id) ON DELETE CASCADE,
  created_at     timestamptz NOT NULL DEFAULT now(),
  created_by     uuid REFERENCES mentorix.users(id),
  CONSTRAINT program_block_clients_program_block_key_client_uniq
    UNIQUE (program_id, block_key, client_user_id)
);

-- Lookups by (program_id) and (program_id, block_key) ride the UNIQUE index's
-- leftmost prefix. client_user_id is its third column, so it needs its own.
CREATE INDEX program_block_clients_client_user_id_idx
  ON mentorix.program_block_clients (client_user_id);
```

Нет строк для `(program_id, block_key)` → блок общий. `publish`,
`publish-update`, `discard-unpublished` и `sync` эту таблицу не трогают.

## Чтение и фильтрация

Единственная точка фильтрации — клиентский путь бота,
`internal/trainerclient/bot_service.go:165`, где сейчас вызывается
`GetVersionDetail(assignment.ProgramVersionID)`.

Вводится `GetVersionDetailForClient(ctx, versionID, programID, clientUserID)`:
грузит ту же `Detail`, догружает правила программы и выбрасывает блоки, у
которых правила есть, а клиента среди них нет. Существующий `GetVersionDetail`
не меняется — им пользуется тренер при просмотре версии.

`buildDaySnapshot` (`internal/workoutcompletion/snapshot.go:27`) строится из
переданного `program.Day`, поэтому в журнал `client_workout_completions` и в
ленту тренера автоматически попадает ровно то, что клиент видел. Отдельных
изменений там не нужно.

## API

```text
PUT /programs/{id}/weeks/{week_id}/blocks/{block_id}/clients
    { "client_user_ids": ["…", "…"] }
```

Полная замена списка (`PUT` = full replace, как у `reorder`); путь на уровне
недели, как остальные операции над `block_id`. Пустой массив → блок снова общий.

Ответ — обновлённый `ProgramDayBlock`.

`ProgramDayBlock` получает поле `client_user_ids: string[]` (uuid), пустой
массив = блок общий. Поле всегда массив, никогда `null`.

Отдаётся в `GET /programs/{id}` — единственном эндпоинте, который возвращает
тренеру дерево блоков. GET на одну версию в API нет: на
`/programs/{id}/versions/{version_id}` висит только `DELETE`.

Внутренний `GetVersionDetail` при этом **обязан** заполнять `BlockKey` и
накладывать правила, и причина не косметическая. Его читает
`discard-unpublished`: рабочая копия пересобирается из замороженной версии, и
если `BlockKey` придёт нулевым, каждый discard сгенерирует блокам новые ключи и
молча порвёт привязку всех правил. Второй читатель — клиентский путь бота,
который поверх этого фильтрует блоки по клиенту.

`block_key` в API не выходит — это внутренняя идентичность.

Кандидатов для пикера фронт берёт из существующего
`GET /programs/{id}/assignments`.

### Ошибки

| Код | Условие |
| --- | ------- |
| `400 last_shared_block` | после изменения в дне не остаётся общего блока |
| `400 client_not_assigned` | в списке клиент, которому программа не назначена |
| `400` | дубли в `client_user_ids`, некорректный uuid |
| `403` | вызывающий не владелец программы (admin тоже `403` — мутация) |
| `404` | программа, неделя или блок не найдены |

Текст `last_shared_block` называет неделю, день и версии, на которых сидят
затронутые клиенты.

## Инвариант «в дне минимум один общий блок»

Проверяется в двух точках:

1. **`PUT …/clients`** — потому что правила применяются к клиентам мгновенно, в
   обход publish.
2. **`publish` / `publish-update`** — потому что это момент, когда изменённый
   контент доезжает до клиентов.

Операции над контентом (`DELETE` блока, `move`, `merge`) отдельно не
проверяются: их результат не виден клиентам до publish, и там их и остановит
валидация. Это совпадает с тем, как проект уже валидирует контент — пустая
группа и формат `sets`/`reps` тоже ловятся на publish, а не при редактировании.

### Против чего проверяет `PUT …/clients`

Один и тот же `block_key` живёт в нескольких деревьях, и клиенты сидят в разных
из них. Проверяются:

- working copy (шаблон) — то, что уедет клиентам при следующем publish;
- каждая версия, на которой висит активное назначение этой программы:

```sql
SELECT DISTINCT program_version_id
FROM mentorix.program_assignments
WHERE program_id = $1;
```

В каждом дереве находится день, содержащий этот `block_key`, и проверяется, что
после изменения в нём остаётся хотя бы один блок без правил. Версии без активных
назначений не проверяются — их никто не читает.

Пример, который отсекается только благодаря проверке версий:

```text
Working copy: день 3 = [A, B, C]      C — общий
Версия 4:     день 3 = [A, B]         на ней 18 клиентов
Версия 3:     день 3 = [A]            на ней 2 отставших клиента

Тренер ограничивает A. По working copy общий C остаётся — пропустили бы.
В версиях 4 и 3 общих блоков не остаётся → 400.
```

### Когда проверка запускается

Инвариант зависит только от того, ограничен блок или нет, а не от состава
списка. Поэтому сломать его может только переход **общий → персональный**.
Смена состава уже ограниченного блока и снятие всех ограничений проверки не
требуют.

## Поведение существующих операций

| Операция | Поведение |
| -------- | --------- |
| `DELETE` персонального блока | Разрешено; правила не удаляются (см. «Чистка») |
| `DELETE` общего блока, в дне есть персональные | Разрешено; ловится на publish |
| `DELETE` последнего упражнения из персонального `single` | Блок удаляется, как сейчас |
| `DELETE` недели / дня | Блоки уходят каскадом, правила остаются до чистки |
| `move` блока в другой день | `block_key` едет с блоком, правила сохраняются |
| `ungroup` персональной группы | Каждый получившийся `single` наследует список группы |
| `extract` упражнения из персональной группы | Новый `single` наследует список группы |
| `merge` блоков с разными наборами клиентов | **`400`** — сначала выровнять списки |
| `discard-unpublished` | `block_key` сохраняются (как `day_key`), правила уцелевают |
| Снятие программы у клиента | Удаляются строки этого клиента по снимаемой программе |
| Смена программы у клиента | Удаляются строки по прежней программе; по новой правил ещё нет |

Отказ `merge` — про несовпадение списков, а не про инвариант дня: слияние не
может уменьшить число общих блоков в дне, поэтому под правило «проверяем только
на `PUT …/clients` и publish» оно не подпадает.

Наследование при `ungroup` и `extract` обязательно: без него разгруппировка
персональной группы молча раскрыла бы её всем.

## Чистка осиротевших правил

Правило осиротевает, когда его `block_key` исчез и из шаблона, и из всех
оставшихся версий программы.

Чистка вешается на существующий best-effort проход `CleanupProgramVersions`,
который уже вызывается после `assign` / `reassign` / `clear` / `sync` и удаляет
версии без активных назначений — то есть ровно тогда, когда правила и
осиротевают:

```sql
DELETE FROM mentorix.program_block_clients pbc
WHERE pbc.program_id = $1
  AND NOT EXISTS (
    SELECT 1
    FROM mentorix.program_week_day_blocks b
    JOIN mentorix.program_week_days d ON d.id = b.program_week_day_id
    WHERE d.program_id = pbc.program_id AND b.block_key = pbc.block_key
  )
  AND NOT EXISTS (
    SELECT 1
    FROM mentorix.program_version_week_day_blocks vb
    JOIN mentorix.program_version_week_days vd
      ON vd.id = vb.program_version_week_day_id
    JOIN mentorix.program_versions v ON v.id = vd.program_version_id
    WHERE v.program_id = pbc.program_id AND vb.block_key = pbc.block_key
  );
```

Тот же запрос без `$1` добавляется в `cleanup.Run`
(`internal/cleanup/janitor.go`) как страховка. **Важно:** `cmd/janitor` сейчас
ничем не запускается по расписанию — ни `render.yaml`, ни workflow в
`.github/workflows/` его не вызывают, хотя `docs/features/garbage-cleanup.md`
упоминает cron. Поэтому основной механизм — проход вместе с
`CleanupProgramVersions`, а не janitor.

Осиротевшая строка безвредна: блока с таким `block_key` больше нигде нет, а
новый блок всегда получает новый ключ. Чистка нужна только чтобы таблица не
росла.

## Что не меняется

Версии, `publish`, `publish-update`, `sync`, `content_fingerprint`
(`internal/program/version_fingerprint.go:48`), `client_workout_completions`,
квоты тарифов.

Аналитика тоже не меняется. «Тренировочный день» — день с ≥1 блоком, а общий
блок в дне гарантирован инвариантом, поэтому набор тренировочных дней одинаков
для всех клиентов: прогресс, drop-off и матрица недели считаются как раньше.

## Риски и ограничения

**Бэкфилл `block_key` для существующих версий — best-effort.** Сопоставление
идёт по `(program_id, week_number, day_number, sort_order)` — стабильной
идентичности у блока до этой миграции не существовало. Расхождение шаблона с
замороженной версией даёт два разных исхода, и второй хуже первого:

- **Блок или день удалён из шаблона** — совпадения нет, замороженный блок
  остаётся со случайным ключом от дефолта. Правила к нему просто не применяются,
  он виден всем. Безопасно.
- **Блоки в дне переставлены местами, а их количество прежнее** — совпадение
  есть, но **не с тем блоком**. Замороженный блок получает ключ чужого блока
  шаблона. Тогда ограничение, поставленное на блок B, скроет у клиентов этой
  версии блок A, а ограничение на A не сделает ничего. Молчаливая ошибка,
  которую ни миграция, ни тест отличить от корректного совпадения не могут.

Это неустранимо для позиционного бэкфилла и тот же класс риска, который уже
принят в `000020` для `day_key`. Риск ограничен клиентами, сидящими на версиях,
опубликованных до миграции: до первой персонализации правил не существует вовсе.
Рекомендация на выкат — синхронизировать клиентов на latest-версию перед тем,
как пользоваться персонализацией.

## Тестирование

- Table-driven на фильтр видимости: общий блок, персональный со включённым
  клиентом, персональный с чужим клиентом, отставшая версия.
- Table-driven на валидатор инварианта: working copy проходит / версия не
  проходит; переход общий → персональный против прочих переходов.
- Handler-тесты нового эндпоинта на каждую ошибку: `last_shared_block`,
  `client_not_assigned`, дубли, `403`, `404`.
- Тесты наследования при `ungroup` и `extract`, запрета `merge`, сохранения
  правил при `move` и `discard-unpublished`.
- Интеграционный тест миграции: `block_key` проставлен, уникальность держится,
  сопоставление шаблон ↔ latest-версия точное.
- Интеграционный тест чистки: правило исчезает вместе с последней версией.
- e2e через бот: два клиента на одной версии видят разный набор блоков; снапшот
  выполненного дня содержит только видимые клиенту блоки.

# Auth

**Status:** implemented  
**Code:** `internal/auth/`

## Purpose

Sign-in with Google and Apple (the mobile app and the web cabinet) and with Telegram through the bot, linking a Telegram to an app account, JWT access token, opaque refresh token (HttpOnly cookie for the web cabinet, JSON body for the app), roles via `user_roles`.

## Database

`users`, `auth_identities`, `auth_refresh_sessions`, `user_roles`, `trainers` (with `terms_version` and `terms_accepted_at`, both null or both set).

## API

Contract: `api/openapi.yaml` (Auth tag).

Key details:

- Access token in JSON. Web cabinet: refresh token only in the cookie; frontend uses `credentials: 'include'`.
- Every token response carries `expires_at` (access token) and `refresh_expires_at` (refresh token), both RFC 3339 in UTC. `refresh_expires_at` is the expiry stored for the refresh session, `REFRESH_TTL_DAYS` from the moment of issue, and it is present in cookie mode too, so a client does not have to compute it. A refresh rotates the token and moves the expiry forward.
- `POST /auth/google` takes a Google ID token. The first sign-in creates a user with the `client` role and an identity `(google, sub)`; later sign-ins return the same user. Name comes from the token (trimmed, cut to 100 characters) and is saved when the account is created. A sign-in into an existing account whose name is empty (blank counts as empty) saves it too; a name that is set is never overwritten. A name cleared with `PATCH /auth/me` therefore comes back at the next sign-in that carries a name. Email is stored only when Google marks it verified, and accounts are never joined by email, so an unverified or missing email leaves `email` empty in the response. Answers: `400` bad body, empty `id_token` or a `nonce` over 256 characters, `401 invalid_id_token` token rejected, `429 rate_limited`, `503 provider_not_configured` when `GOOGLE_CLIENT_IDS` is empty. It uses the login rate limit.
- The ID token must be signed by Google, issued by `https://accounts.google.com`, unexpired, and addressed to one of the ids in `GOOGLE_CLIENT_IDS` (comma separated). Google's signing keys are fetched with a 5 second timeout. Any failure answers `401`, including a Google outage.
- `POST /auth/apple` works the same way with an Apple ID token (issuer `https://appleid.apple.com`) and an identity `(apple, sub)`. `APPLE_CLIENT_IDS` (comma separated) holds the iOS bundle id and, for Android, the Services ID. Apple does not put the name in the token, so the app sends it as the optional `name` in the request body. It is trimmed, cut to 100 characters without an error, and follows the same rule as the Google name: saved on creation and filling an empty name of an existing account, never replacing a set one; a name claim in the token wins over it. Apple sends `email_verified` as a boolean or as a string, and both are accepted. Answers and codes as for Google, plus `400 nonce_required` when `nonce` is empty or absent, and with `503 provider_not_configured` when `APPLE_CLIENT_IDS` is empty. The body is checked first, so a `400` comes before the `503`.
- **Nonce.** `POST /auth/apple` requires `nonce`; `POST /auth/google` takes it as an option, because the Flutter `google_sign_in` package sets a nonce only once at startup and the mobile app cannot send one per sign-in. The app passes the provider the SHA-256 of the raw value as lowercase hex and sends the raw value to us. When `nonce` is set, the token's `nonce` claim must equal that hash, compared in constant time; a missing claim or a mismatch answers `401 invalid_id_token`, like any other token failure. On Google an empty or absent `nonce` skips the check. On Apple it answers `400 nonce_required` before the token is checked; the handler refuses it, and the service refuses it too, so no other caller can skip the check. Over 256 characters answers `400`. The nonce is not logged, and the error cause names neither value.
- `POST /auth/apple/callback` is the return address of Sign in with Apple on Android. The flow runs in a browser tab and Apple ends it by posting a form (`application/x-www-form-urlencoded`) here. The endpoint is public, creates no session, checks no token and touches no database or Redis. It answers `307` with `Location: intent://callback?<form fields>#Intent;package=<APPLE_ANDROID_PACKAGE>;scheme=signinwithapple;end`, which opens the app; the app then sends the `id_token` to `POST /auth/apple`. Every field of the form body is copied and re-encoded, so a value cannot change the part after `#`; the URL query string is ignored. The answer carries `Cache-Control: no-store` and nothing from the body is logged, because the link holds the ID token and the authorization code. The server does not check `state`: the app starts the flow, so only the app can compare it on return. Answers: `400` for a content type other than a form, a body that cannot be parsed, or an empty form; `413` over 16 KB (the global limit is 1 MB); `503` when `APPLE_ANDROID_PACKAGE` is empty. Its errors keep the code of their status (`bad_request`, `payload_too_large`, `service_unavailable`). `APPLE_ANDROID_PACKAGE` must be a dotted Android package name, checked at startup. No rate limit.
- Google and Apple sign-in return `refresh_token` in the JSON body and set no cookie. `POST /auth/refresh` and `POST /auth/logout` accept `{"refresh_token": "..."}` as a JSON body: refresh then returns the rotated token in the body and logout revokes it, and neither sets or clears a cookie. Without a token in the body (no body, no JSON content type, empty value) both work as before with the cookie, and the response has no `refresh_token`. A body that cannot be read counts as no token and takes the cookie path.
- **Telegram link.** `POST /auth/telegram/link` (Bearer JWT, login rate limit, body `{code}`) joins a client who signed in with Google or Apple to the Telegram they already use. The client opens the bot with `/start link`; the bot answers with a one-time code (8 characters, valid 10 minutes, key in [redis-naming.md](../../.claude/rules/redis-naming.md)), and the client types it into the app. The direction is deliberate: the secret travels from the Telegram owner to the app, so nobody can push their own sign-in onto someone else's account. The code is read and deleted in one step, so it works once, and it is spent even when the link is then refused. Case and surrounding spaces are ignored. Outcomes, decided in one transaction:
  - The Telegram has no account yet: it is attached to the caller's account. The answer carries new tokens for the same user. Two parallel requests for the same account and Telegram both succeed.
  - The caller's account already holds this same Telegram: nothing changes, the answer still carries new tokens.
  - The Telegram already has an account and the caller's account is empty (no trainer link, no role besides `client`, no sign-in besides Google and Apple): the caller's Google and Apple identities move to the Telegram account, its email is filled from the caller's only when it has none, it gets the `client` role if missing, and the caller's user is deleted with its refresh sessions. The tokens in the answer belong to the Telegram account, so the app replaces its own. The merge checks emptiness again after it locks both user rows, the lower id first, so a "Become a trainer" or an account deletion of either side at the same moment either waits for the merge or is seen by the check.
  - The Telegram has an account and the caller's account is not empty: `409 telegram is linked to an account that cannot be merged`, nothing changes. The same answer is given when the Telegram account is an admin (an admin cannot hold the `client` role), when the Telegram account was deleted while the merge waited for it, or when the database refuses to delete the caller's user because other rows still reference it; the whole change is rolled back. Two accounts with data are resolved by hand.
  - The caller's account holds a different Telegram: `409 account already has another telegram`.
- Telegram link answers: `200` tokens in the body (`refresh_token` included, no cookie), `400 invalid_link_code` (`invalid or expired code`: empty, unknown, expired or already used), `401` no token, `404 user_not_found` the caller's account is gone, `409 telegram_link_conflict` or `409 telegram_already_linked` as above, `429 rate_limited`, `503 telegram_link_unavailable` (`telegram linking is unavailable`) when Redis is not configured or down. Unlinking and moving a Telegram between accounts are not supported.
- `GET /auth/me` and `PATCH /auth/me` return `telegram_linked` (always present): true when the account has a Telegram sign-in, so the app can ask "already training through Telegram?" right after the first sign-in.
- **Become a trainer.** `POST /auth/me/trainer` (Bearer JWT, body `{terms_version}`, at most 16 KB) makes the caller a trainer without taking anything away: the `trainer` role is added next to the roles they hold (a Google or Apple client keeps `client`), a trainer profile is created when there is none (an older trainer account already has one), and the version of the trainer terms the person accepted is stored with the time. `terms_version` is a calendar date, `YYYY-MM-DD`; surrounding white space is trimmed and any other form (`2026-10-1`, `2026-02-30`, a timestamp, empty or missing) is `400 bad_request`. The call is idempotent: the same version again changes nothing and keeps the time of the first acceptance, another version replaces both the version and the time. A trainer whose profile was created before this call existed has no version until the call records one. The plan of a new trainer is `free` without an entitlement row, see [subscriptions.md](subscriptions.md). The answer is the profile as `GET /auth/me` returns it, `200` on the first call and on every repeat. The change is one transaction that locks the trainer profile, if there is one, and then the user row, the order quota writers use. Answers: `200`, `400`, `401`, `403 admin_cannot_activate` (an admin cannot hold the trainer role; nothing changes), `404 user_not_found`, `413`, `500` (`trainer activation failed`, the cause in the log only). After the activation the account is no longer empty for the Telegram link, which treats any role besides `client` as data.
- Rate limiting on sign-in (Google, Apple, Telegram link) and refresh by client IP (how it is found: `TRUSTED_PROXY_CIDRS` in [environments.md](../environments.md)) when `REDIS_URL` is set. Sign-in shares one counter, the login limit (`AUTH_LOGIN_RATE_MAX`, `AUTH_LOGIN_RATE_WINDOW_SEC`); refresh uses the same values with its own counter key. Every `429 rate_limited` carries `Retry-After` with the whole seconds left in the window (at least 1), read in the same Redis call as the counter. If Redis is unavailable, requests are allowed and a warning is logged; sign-in does not depend on Redis. The dashboard's server can forward the browser address in `X-Mentorix-Client-IP` with the shared secret in `X-Mentorix-BFF-Secret`, and the limits then count by that address (see [environments.md](../environments.md)).
- Limits: display name 100 characters (`PATCH /auth/me`), counted in runes; over the limit answers `400`.
- Unknown paths answer `404`, except under `/programs`, `/exercises`, `/trainer` and `/admin`: those groups carry the JWT middleware on their prefix, so an unknown path there answers `401` without a token. In `/auth`, only `/auth/me`, `/auth/me/trainer`, `/auth/logout-all` and `/auth/telegram/link` require a token.
- **Error codes.** Every error body is `{code, message}`; `code` is stable, `message` may change. Besides the ones above: `missing_refresh_token` and `invalid_refresh_token` (refresh `401`), `user_not_found` (`GET`, `PATCH` and `DELETE /auth/me` and `POST /auth/me/trainer` `404`), `admin_cannot_activate` (`POST /auth/me/trainer` `403`), `account_deletion_unavailable` (`DELETE /auth/me` `409`), and for the Apple revocation of the same call `apple_authorization_required` (`422`), `apple_account_mismatch` (`403`), `invalid_apple_authorization_code` (`400`) and `apple_revocation_failed` (`502`), see [account-deletion.md](account-deletion.md), `missing_authorization` (no `Authorization` header, or not a Bearer token) and `invalid_token` (the JWT middleware, on every protected route), `rate_limited` (every `429` of Google, Apple, refresh and Telegram link). Any other error, invalid JSON for one, has the code of its status (`bad_request`).
- JWT signed with HS256.
- `POST /auth/logout-all`, `GET /auth/me`, `PATCH /auth/me` (changes the display name), `POST /auth/me/trainer` (becomes a trainer, above) and `DELETE /auth/me` (deletes the account, see [account-deletion.md](account-deletion.md)) require Bearer JWT.

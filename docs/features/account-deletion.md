# Account deletion

**Status:** implemented  
**Code:** `internal/auth/account_deletion.go`, `internal/auth/apple_revoke.go`, `DeleteMe` in `internal/auth/handlers.go`, wiring in `internal/app/routes.go`

## Purpose

A client, or a trainer who has no business data, deletes their own account from the mobile app, as the App Store requires, and every row that belongs to them goes with it. Nothing is kept: no soft delete, no grace period, no anonymous copy. An account that signs in with Apple has its Apple authorization revoked first, which Apple asks for.

## Database

No table of its own and no migration. One transaction deletes the rows of a single account, in this order:

1. `program_assignments`, then
2. `client_workout_completions`, which cascade `client_workout_completion_comments` (the trainer's replies). The order is the one a trainer's removal of an assignment takes (the foreign key action clears the completions' link), so the two transactions never lock the rows the other way round.
3. `trainer_invites` the client consumed. A consumed invite cannot lose its `consumed_by` (`trainer_invites_consumed_check` needs both columns set or both null), so the foreign key's `SET NULL` would be refused. Consumed invites are purged after 7 days anyway.
4. `users`, which cascade `auth_identities`, `user_roles`, `auth_refresh_sessions`, `user_link_codes`, `trainer_clients` and `program_block_clients`, and `trainers`, which cascades the trainer's own `trainer_invites` (active and consumed) and admin-granted `trainer_plan_entitlements`.

The programs, versions and exercises of other trainers, and every other client, are not touched. Deleting an account does not run the program version cleanup, see [garbage-cleanup.md](garbage-cleanup.md).

## API

Contract: `api/openapi.yaml` (`DELETE /auth/me`, `deleteMe`).

Key details:

- Bearer JWT, no cookie set or cleared, no rate limit. Success is `204` with no body. The body is optional JSON (`DeleteAccountRequest`, at most 16 KB): none, an empty or a blank one is valid, with any Content-Type. A body with text needs `Content-Type: application/json` (case and parameters such as `charset` do not matter), otherwise `400`. The Apple fields are read from the body only, never from the query string.
- **Who.** Only an account whose roles are exactly `client`, exactly `trainer`, or both. An `admin` role, alone or next to another, and an account with no role row are refused. A trainer is deleted only while the trainer side holds no business data (below). The transaction locks the trainer's invite rows first (accepting an invite locks its row before the `trainers` row), then the `trainers` row, when there is one, then the user row (`FOR UPDATE`), the order the other writers use, and decides every refusal under those locks, so a role, trainer data or an Apple sign-in added a moment earlier is seen. An invite accepted at the same moment normally commits first, so its new client makes the deletion refuse, or finds the invite gone. Known windows, each ending in a database error (`500`) with nothing changed, where a repeat works: an invite created after the invite rows were locked and accepted before the delete cascade reaches it can deadlock with the deletion, and so can the janitor's purge of stale invites, which deletes rows in scan order. When "become a trainer" commits between the lookup of the `trainers` row and the user lock, a quota writer on the new row can deadlock with the deletion; one of the two fails with `500`, nothing is changed, and a repeat works. A trainer who assigns a program to the client at the same moment either commits first, and the assignment is deleted with the rest, or fails because the user is gone.
- **Trainer business data.** Any one of these refuses the deletion, for every account: a `trainer_clients` row of the trainer (any status, blocked included); a program the account created or last edited, a program week, day or block exercise it last edited, a program version it published (the database cannot detach the account from these rows); an exercise the account created or last edited or the trainer owns (soft-deleted ones count); a program assignment made or last edited by the account, or for the trainer; a workout completion or a comment on one by the trainer; a block visibility rule the account created; a plan entitlement from `app_store` or `google_play` in any status, because store-paid plans are payment data. Not data, removed with the account: the trainer's invites (active and consumed), admin-granted entitlements, the `trainers` row and the `trainer` role. A trainer who is also a client has the client data above deleted as for any client.
- **Refusal.** `409 account_deletion_unavailable` (`this account cannot be deleted in the app`) for an admin, an account with no role, a trainer with business data, and also when the database refuses the delete because other rows still reference the user. Nothing is changed.
- **Answers.** `204` deleted; `400` an invalid body (`bad_request`: invalid JSON or another Content-Type, one of the two Apple fields without the other, a redirect address that is not an absolute `https` URL without a fragment or is longer than 2048 characters) or `invalid_apple_authorization_code` (Apple refused the code); `401` no token or a bad one (`missing_authorization`, `invalid_token`) or `invalid_id_token`; `403 apple_account_mismatch`; `404 user_not_found` (the account is already gone, so a repeated call answers `404`); `409 account_deletion_unavailable`; `413` over 16 KB; `422 apple_authorization_required`; `502 apple_revocation_failed`; `503 provider_not_configured` (`apple account deletion is not configured`); any other failure is `500` (`account deletion failed`) with the cause in the log only. No answer except `204` deletes anything.
- **Apple.** An account with an `apple` sign-in is revoked at Apple before anything is deleted. Right before the call the app runs Sign in with Apple again and sends `apple_id_token`, `apple_authorization_code` and, on Android only, `apple_redirect_uri`: the address it gave Apple. iOS sends none because its authorization request has none. A code is single use and lives five minutes. The service answers at the first check that fails. The checks before Apple take no lock, so they catch what is already there, not what arrives later. Verifying the token (step 4) may refetch Apple's public keys; the token and revoke endpoints are called only after the fifth check passes:
  1. the roles are `client`, `trainer` or both and the trainer side holds no business data, else `409`; the store checks again under its locks;
  2. the revocation is configured (`APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY`) and Apple sign-in has client ids (`APPLE_CLIENT_IDS`), else `503`;
  3. the body has the token and the code, else `422`;
  4. the token passes the sign-in verifier (signature, issuer, expiry, audience in `APPLE_CLIENT_IDS`), else `401`;
  5. the token's subject is one of the account's Apple identities, else `403`.
- **Revocation.** The server signs a client secret per request (an ES256 JWT of the team's `.p8` key, valid five minutes), trades the code for a refresh token at Apple (`client_id` is the audience of the token, `redirect_uri` only when sent), and revokes that token. The code must belong to the same Apple account as the token: the exchange answer carries an ID token of the account the code was issued to, read without a signature check (it came from Apple's host over TLS in answer to our own request). Its subject must be the one just proven, its issuer Apple, and its audience must contain the `client_id`. Another subject is `403 apple_account_mismatch` and nothing is revoked; an unreadable token, or one for another issuer or client, is `502`. The Apple step has one 10 second budget for both calls; each call also has its own 10 second timeout. A key refetch during the token check (step 4) can add up to 5 seconds before the budget starts, and the server's write timeout is 15 seconds, so the answer can be lost while the delete still happens: a repeat then answers `404`. Apple's `invalid_grant` on the exchange (wrong, expired, used, or issued for another client) is `400 invalid_apple_authorization_code`. Every other refusal, an unreadable answer, a timeout (10 seconds) and a transport error are `502 apple_revocation_failed`; `invalid_client` lands there too, from a wrong `apple_redirect_uri` or a wrong key. Redirects are not followed and answers are read up to 64 KB. The log names the step and Apple's `error` value or HTTP status. The code, the tokens and the client secret never reach a log or an answer, and nothing from Apple is stored.
- **Order.** Checks, then Apple, then the database. A failed revocation deletes nothing and can be repeated with a new authorization. The same goes for a role or trainer data that arrives between the checks and the store's locks, for example a client accepting the trainer's invite during the Apple call: Apple has revoked, the store answers `409`, the account stays, and the person signs in with Apple again and repeats. The store checks again under its lock that the revoked subject is one of the account's Apple identities, so an Apple sign-in that arrived after the checks is refused: `422`, or `503` when the revocation is not configured. Once Apple confirmed, the delete runs on a context of its own with a 10 second limit, so it finishes even if the app drops the connection. If the database fails after Apple confirmed, the account is still there: the person signs in with Apple again and repeats. An account without an Apple sign-in ignores the Apple fields (their shape is still checked) and never reaches Apple. Known limit: an account with two Apple identities is deleted once one of them is revoked; the other authorization stays at Apple.
- **Invites and blocks.** The invites the client used are deleted, so tapping the link of one answers `invite_not_found` instead of `invite_consumed`. A trainer's block of the client goes with the account: a person who deletes the account and later joins with a fresh invite of that trainer is a new client and is not blocked.
- **Sessions.** Refresh sessions go with the user. An access token issued earlier works until it expires (`ACCESS_TTL_MINUTES`, 15 by default) and finds nothing: `GET /auth/me` answers `404 user_not_found`. The app clears its own tokens.
- **Telegram.** The Telegram sign-in goes with the account. After the commit the bot's `active_trainer` key for that Telegram is removed (key in [redis-naming.md](../../.claude/rules/redis-naming.md)). The removal runs on its own context with a 5 second limit, so a client that drops the connection after the commit does not cancel it. A failure there is logged as a warning and the request still succeeds. `workout_pending` (30 minutes) and `avatar_checked` (24 hours) expire by themselves. For the bot the person is unknown again, and accepting an invite later creates a new empty account.
- **Coming back.** Signing in again with the same Google or Apple account creates a new empty account.
- **Log.** One info line `account deleted` with `user_id`. A cleanup failure logs a warning with the user id and the error. Nothing personal reaches the log.
- The trainer is not told that a client left. Their client list, progress and history lose the client. A trainer account is deleted only when it has no clients, so nobody loses a trainer.
